## 一个概念：固定截止时间

例如周一 20:00 登录，下周一 20:00 到期。周日刷新仍按原期限；到期后重新登录，再从这次登录开始七天。服务重启和正常关闭重开浏览器也不会重算期限。

成功登录时，T004 已将服务器当前时间加七天交给 `request.session.set_expiry()`。浏览器保存持久 Cookie，服务器数据库保存当前身份和到期时间；每次请求查找有效会话，到期就先去登录。[Django 会话说明](https://docs.djangoproject.com/en/5.2/topics/http/sessions/#django.contrib.sessions.backends.base.SessionBase.set_expiry)

`set_expiry(604800)` 的整数表示相对会话修改时间的时长；本项目传入具体日期时间，让以后的普通会话写入也沿用原截止时间。本课验证已有实现，无须重新写登录代码。

## 怎样不用等一周就验证

新增的 `core/tests/test_sessions.py` 用测试时钟；只改变本次测试所见时间，不修改系统时钟。Django 日期和 Cookie 日期采用同一模拟时钟，测试只用临时内存数据库。

| 测试时刻/操作 | 实际结果 |
|---|---|
| t0 登录 | 保存 t0+7 天，Cookie 可跨浏览器重开保留 |
| 第六天浏览首页、工作台、已登录的登录页 | 身份与截止时间不变，未重发会话 Cookie |
| 第六天写入普通会话字段 | 字段保存成功，仍在 t0+7 天到期，Cookie 剩余一天 |
| 到期前一秒 | 能进入工作台 |
| 到期时与之后一秒，主动重放旧 Cookie | 服务器拒绝个人访问，先去登录 |
| 到期后重新登录 | 开始新的七天，旧 Cookie 继续无效 |
| A、B 在相隔一天的时间登录 | A 到期时 B 仍有效，各自期限独立 |

5 项新测试与原 46 项共 **51 项通过**；Django 配置与迁移一致性通过。测试前后用户数据库、密钥内容和修改时间未变。
