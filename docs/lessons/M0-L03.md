# M0-L03：把改动通过 GitHub PR 交付

## 本课目标

让 Agent 完成建仓、推送、Issue、PR、检查、审查和合并；你认识每个结果在哪里，学习怎样发出范围明确的交付指令。终端操作由 Agent 执行。

## 本课真实地址

- [公开源码仓库](https://github.com/zhanag61/studyhub)
- [Issue #1：目标与验收](https://github.com/zhanag61/studyhub/issues/1)
- [PR #2：实际改动、检查与审查](https://github.com/zhanag61/studyhub/pull/2)
- [GitHub Actions：自动检查](https://github.com/zhanag61/studyhub/actions)

公开源码仓库建立后，网站仍运行在本地；M0-L04 才处理真实网站部署。

## 这次实际发生的流程

1. Agent 检查干净的工作区、GitHub 当前账号和同名仓库，使用已有登录创建公开仓库。
2. 推送 main 起步基线和 feat/m0-welcome-message 功能分支。本次不用重复手工登录，也未安装 GitHub CLI。
3. 创建 Issue #1，记录为什么修改首页、具体目标和验收条件。
4. 创建 PR #2，base 为 main，head 为 feat/m0-welcome-message；描述页面实际行为、已有验证和对应规范。
5. GitHub Actions 运行 Django 配置和迁移一致性检查；独立 Agent 对照规范审查差异。具体结果以课程日志和 PR 为准。
6. 检查与审查完成后，把用户已经验收的改动 Squash and merge 到 main，再同步本地 main 并验证工作区。

## 四个概念

| 名称 | 本课中的作用 | 你看哪里 |
|---|---|---|
| 仓库 | 在 GitHub 保存项目源码和版本历史 | 仓库的 Code 页 |
| 分支 | main 保留起步版本，功能分支保存首页修改 | 分支选择器 |
| Issue | 写清要解决的问题和验收目标 | Issue #1 |
| PR | 对比功能分支与 main，记录检查和审查，完成合并 | PR #2 的 Files changed、Checks |

Squash and merge 把功能分支的多次提交合成 main 中的一次提交。main 的提交编号会变化，这是该合并方式的正常结果。PR 仍保留整个讨论、差异和检查记录。

## 发给 Agent 的指令练习

> 把当前已经验收的本课改动通过 PR 交付。检查当前分支和范围，关联 Issue，运行相关检查，让另一位 Agent 按规范审查。修复实际问题，检查通过后合并，并同步本地 main。告诉我仓库、PR、检查结果和下一步，由你执行 Git 操作。

这条指令包含范围、验收前提、交付方式和证据要求。以后每项小功能都能沿用，只替换本课目标。

## 用户实际参与

打开 PR #2，看看 Files changed 中的主标题和区域配色改动，再看 Checks 的实际结果。尝试用一句话描述 PR 的作用；这项理解只根据你的反馈记录，不用重复终端命令。
