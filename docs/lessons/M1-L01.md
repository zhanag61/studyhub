# M1-L01：先把登录行为说清楚

## 本课目标

确认已有测试账号怎样登录、看到什么、怎样处理错误和退出，保存一份双方认可的 [spec.md](../../specs/001-login/spec.md)。目前处于需求澄清，本课完成的依据是用户确认规范，不是生成了文件或写出了代码。

## 一个概念：规范是行为约定

「做登录功能」可以有许多不同实现。下面这句话可以直接操作、观察和验收：

> learner_a 输入错误密码后留在登录页，看到「用户名或密码不正确」，用户名保留，密码框清空。

它说明谁在什么情况下做什么，以及结果是什么。写 spec.md 就是把这样的预期保存下来，后续 Agent 按它实现，你按它验收。

| 文档 | 回答的问题 | 本轮课程 |
|---|---|---|
| spec.md | 使用者做什么，应该看到什么 | 本课确认 |
| plan.md | 在当前项目怎样实现这些行为 | M1-L02 |
| tasks.md | 分几步做，每步怎样验证 | M1-L02 |

这就是第一轮手工 SDD。到 M2 才引入 Spec Kit，当前不需要安装新工具。

## 你的参与

只决定会改变使用体验的规则。环境、Django 配置和 Git 操作由 Agent 处理。需求问题提供推荐选项；你可以采用推荐，也可以用自己的话修改。

收到完整规范后，可发这条**聊天指令**：

> 我确认这份登录规范。把本课已决定的行为保存为规范并更新课程日志；本课不写业务代码。下一课再写 plan.md 和 tasks.md。

若有不同预期，可以这样发：

> 修改验收例子 A004：错误密码时我希望看到「……」。先更新规范并解释影响，等我们确认后再实现。

本课不需要在 PowerShell 输入命令。规范中的密码都是描述，不要把真实密码贴到聊天或提交进仓库。

## 一个小练习

把「支持退出」改写成一句可验收的话。可以沿用这个句式：

> 当我……，页面应该……；如果我再……，应该……。

例如「当我点击退出，页面回到公开首页；如果我再打开个人工作台，应该先去登录」。练习是否完成只根据你的实际回答记录。
