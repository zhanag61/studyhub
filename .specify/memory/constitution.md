# StudyHub Constitution

## Core Principles

### I. 先确认行为，再实现

业务变化必须先写使用场景、范围、验收条件和不包含内容，并取得用户确认；
随后编写技术计划和可验证的小任务，再实现已授权任务。发现需求变化先更新规范，
不把生成的文档或任务清单视为用户确认或已经实现。这样能用双方约定的结果判断完成。

### II. 使用已有 Django 能力，小步交付

采用 Python、Django 5.2 LTS、服务端 HTML/CSS 与少量 JavaScript，复用已有认证、
表单、模板、ORM 与测试设施。每课默认只完成一个可观察行为或明确的工具准备结果，
依最新授权确定范围；不提前生成后续模块。新增依赖须有当前任务的具体理由，
开发工具与网站运行环境分开，先选择能被单人理解和维护的最小方案。

### III. 服务端验证身份与数据归属

从有效登录会话取得当前身份。引入业务模型时记录所属用户，在每次对象读取与写入时
验证归属；不得信任表单传入的 owner、用户名或进度。状态修改使用 POST 和 CSRF，
数据库会话沿用已确认的固定七天期限与主动退出规则。真实密码、密钥、连接串、
数据库与备份不得进入 Git、公开文档或日志。

### IV. 以真实证据验收，区分证据来源

运行与改动有关的配置、迁移一致性和有意义的行为检查；涉及权限、会话、表单错误与
进度计算时验证正常流程和关键边界。CI 必须读取实际运行结果；静态审查、模拟手机、
本地浏览器、用户实机反馈与线上检查分别记录。不得把 Agent 通过写成用户已操作、
已理解或已掌握，也不得以代码存在或 PR 合并替代实际发布成功。

### V. Git 保存过程，Agent 与用户各负其责

每项功能采用 Issue、短期分支、小步提交、验收、PR、只读 Agent 审查与必要修复，
通过后 Squash 合并并同步 main。保留用户改动，不强推或用 reset --hard 清场。
Agent 负责环境、文件、Git、实现和检查；用户决定需求、确认规范与实际使用验收。
终端命令练习由用户自选，默认用聊天指令协作，每课记录成果、问题与下一步。

## 技术与产品约束

本地使用 SQLite，公开多用户服务使用外部持久 PostgreSQL。保留当前 Render Free 与
Neon Free 路线，正式邀请前验证国内普通网络、电脑/手机、持久性与隔离备份恢复。
月新增费用约 50 元，付费前核算总费用。免费休眠和实际部署方式必须如实记录。

首批邀请 5–20 人，邀请码注册和生产账号准备按 M4 推进；当前不开放注册。
任务只有未完成/完成两种状态，允许取消完成；进度按完成数/总任务数计算，空计划 0%。
具体计划字段、表单与删除行为在后续规范确认，不能依据模板示例当作已定需求。

## 开发与课程流程

恢复时读取 README、课程日志、AGENTS 和对应规范，核对 Git 分支与工作区，
并单独核对 `.specify/feature.json` 的活动规范；切换 Git 分支不会自动切换该指针。
没有活动规范时不得静默采用历史已交付功能。先明确本课可见结果、必要概念与分工。

Spec Kit 命令沿用规范、澄清、计划、任务、一致性检查、实施、完整性检查流程。
实施必须限定到已授权任务；模板中的示例、并行提示和“执行全部”不得扩大课程范围。
按项目约定执行必要检查，不为了模板添加重复测试或未经授权的新架构。

合并前核对真实 CI、规范差异、独立审查和已有用户反馈；涉及发布时检查实际部署
commit 与公开请求。现有公开仓库 URL 服务先核对部署记录，必要时手动发布，
不修改生产数据来验证开发工具。已交付的 feature 目录保留为历史；后续修复创建
独立记录并链接原规范，避免把旧验收证据改写成当前结论。

## Governance

本文件是已确认 StudyHub 路线与仓库工作约定的工具表达。用户当前指令优先；
不能因为模板而要求重复确认已授权操作，或擅自扩大实现和发布范围。
AGENTS.md 记录操作细节，课程日志记录实际状态，业务 spec 记录已确认的功能合同。

修改规则时说明具体原因与影响，改变产品行为或既定取舍须由用户确认。
不兼容原则变更升主版本，新增原则或实质扩展升次版本，文字澄清升补丁版本；
更新日期并在课程日志记录影响。每次计划和审查读取本文件，核对兼容性和范围。
1.0.0 是初次整理已有约定，不引入新的产品决定或待补占位符。
